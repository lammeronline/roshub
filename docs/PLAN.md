# ROSHub — план

Модульная экосистема скриптов для MikroTik RouterOS 7: ядро с менеджером модулей и обновлениями из GitHub,
шина уведомлений с отдельными каналами, управление через Telegram, мониторинг здоровья роутера и контроль
WireGuard-туннелей с учётом падений и трафика.

Целевая платформа: RouterOS **7.25+** (проверяется на Chateau LTE6 AX, arm64, 1 ГБ RAM, 128 МБ flash).

---

## 1. Ограничения RouterOS, от которых зависит архитектура

| Ограничение | Что из этого следует |
|---|---|
| Нет `include`/`import` между скриптами | Общий код живёт в **глобальных функциях** (`:global rhLog do={...}`), которые ядро регистрирует при загрузке. Модули вызывают их, а не друг друга напрямую. |
| Глобальные переменные пропадают при перезагрузке | Загрузчик запускается планировщиком `start-time=startup` и заново регистрирует функции и модули. Состояние, которое должно пережить перезагрузку, пишется в файл. |
| Flash 128 МБ с ограниченным ресурсом записи | Частое состояние — в памяти (globals); на диск — редко и пачкой (раз в N минут). Если есть `/usb1`, данные пишем туда. |
| `/file get contents` и `fetch as-value` ограничены по размеру | Один файл модуля — до ~32 КБ; большие модули разбиваются на несколько скриптов. |
| Исходник скрипта виден всем пользователям с правом `read` | Секреты (токены ботов, пароли SMTP) хранятся в отдельном скрипте `rh-secrets`, никогда не попадают в репозиторий; в документации предупреждение о группах пользователей. |
| JSON есть только с 7.13+ (`:serialize`/`:deserialize`) | Манифест и состояние — в JSON; минимальная версия RouterOS проверяется при установке. |
| Нет вебхуков без белого адреса и проброса | Telegram — через long polling `getUpdates` по планировщику. |

Каждое такое допущение (лимиты размеров, `builtin-trust-anchors`, права `fetch`) проверяется на тестовом CHR
до того, как на него опирается код — см. этап 0.

## 2. Архитектура

```
                 GitHub (public): manifest.json, core/, modules/*
                               │  /tool fetch (HTTPS, проверка сертификата)
                               ▼
┌──────────────────────────── RouterOS ─────────────────────────────┐
│  rh-core  ── loader: при старте регистрирует функции и модули     │
│     ├─ rhLog       уровни, префикс модуля, кольцевой буфер        │
│     ├─ rhConfig    чтение настроек (rh-config) и секретов         │
│     ├─ rhState     сохранение состояния модулей в файл (пачкой)   │
│     ├─ rhEvent     публикация событий → подписчики                │
│     └─ rhPkg       install / remove / update / list / check       │
│                                                                   │
│  События: health.*, wg.*, traffic.*, core.update.* …              │
│     │                                                             │
│     ├──► notify (шина) ──► notify-telegram / -email / -ntfy /     │
│     │                      -webhook / -whatsapp / -viber          │
│     └──► журнал                                                   │
│                                                                   │
│  health      проверки по расписанию, пороги, гистерезис           │
│  wg          профили туннелей, переключение, история падений      │
│  traffic     счётчики интерфейсов: сутки / месяц, переживают      │
│              перезагрузку                                         │
│  tg-control  /команды из Telegram → реестр команд модулей         │
└───────────────────────────────────────────────────────────────────┘
```

### Соглашения
- Все объекты ROSHub на роутере имеют префикс `rh-`: скрипты `rh-<module>[-<part>]`, планировщик `rh-<module>`,
  глобалы `rh<Name>`, комментарии маршрутов/правил `RH:<module>:<what>`. Удаление модуля = удаление всего с его
  префиксом; чужие объекты не трогаются.
- Модуль не обращается к другому модулю напрямую — только через функции ядра и события. Тогда любой модуль
  можно удалить, не ломая остальные.
- Событие: `{name; level; module; text; data}`. Уровни: `debug`, `info`, `warn`, `crit`. Повторяющееся событие
  с тем же ключом шлётся один раз до смены состояния (дедупликация).
- Каждый модуль описан в `module.json`: имя, версия (semver), минимальная версия ядра и RouterOS, зависимости,
  список файлов, нужные политики, настройки по умолчанию.

### Репозиторий
```
ROSHub/
├── manifest.json          индекс модулей и версий (генерируется tools/)
├── bootstrap.rsc          однострочная установка ядра
├── core/                  rh-core и его части
├── modules/
│   ├── notify/            шина уведомлений (маршрутизация, очередь, повтор, лимиты)
│   ├── notify-telegram/
│   ├── notify-email/
│   ├── notify-ntfy/  notify-webhook/  notify-whatsapp/  notify-viber/
│   ├── tg-control/
│   ├── health/
│   ├── wg/
│   └── traffic/
├── tools/                 сборка manifest, проверка синтаксиса, выкладка на тестовый CHR
├── tests/                 сценарии для CHR
└── docs/
```

### Установка и обновления
- Установка ядра: одна команда `/tool fetch … bootstrap.rsc; /import bootstrap.rsc`.
- Модули качаются **с тега релиза** (`v1.4.0`), а не с `main` — на роутер не попадает недоделанный код.
- `rhPkg check` раз в сутки сравнивает установленные версии с `manifest.json` и шлёт событие `core.update.available`.
  Автообновление — по флагу на модуль (по умолчанию выключено).
- Перед обновлением текущая версия модуля сохраняется (`rh-<module>.bak`); при ошибке загрузки — откат.

## 3. Модули

### 3.1 Ядро (`core`)
- Загрузчик, регистрация функций, реестр установленных модулей с версиями.
- Конфиг `rh-config` (обычные настройки) и `rh-secrets` (токены, пароли) — на роутере, не в репо.
- Журнал: `rhLog` → `/log` с префиксом `RH:<module>`, кольцевой буфер последних N записей в памяти
  (для `/log` в Telegram), уровни фильтруются настройкой.
- Менеджер пакетов: `install`, `remove`, `update`, `list`, `check`, `rollback`.
- Самодиагностика: какие планировщики модулей не запускались дольше ожидаемого.

### 3.2 Уведомления (`notify` + каналы)
- Шина: принимает событие, по правилам маршрутизации (уровень, модуль, имя события) выбирает каналы.
- Очередь с повторами, если канал недоступен (например, интернет пропал) — отправка после восстановления.
- Лимит частоты и склейка пачки однотипных событий в одно сообщение.
- Каналы — отдельные модули с одной функцией `send`:
  - **Telegram** — Bot API `sendMessage`.
  - **E-mail** — встроенный `/tool e-mail`.
  - **ntfy / Gotify / webhook** — простой HTTP POST, удобно для своих серверов.
  - **WhatsApp** — только через сторонний шлюз (Green API, CallMeBot, Twilio); выбирается при реализации.
  - **Viber** — Bot API требует коммерческий аккаунт; проверить актуальные условия перед реализацией.

### 3.3 Управление через Telegram (`tg-control`)
- Long polling `getUpdates` раз в 5–10 с, `offset` хранится в памяти и периодически на диске.
- Белый список `user_id`/`chat_id`; все остальные сообщения игнорируются и пишутся в журнал.
- Реестр команд: каждый модуль регистрирует свои (`/health`, `/wg`, `/traffic`, `/update`…).
  Встроенные: `/status`, `/modules`, `/log`, `/help`.
- **Никакого выполнения произвольного кода** из чата. Запуск скриптов — только из явного списка разрешённых,
  опасные действия (перезагрузка, отключение туннеля, обновление) — с подтверждением кнопкой.
- Инлайн-кнопки для частых действий.

### 3.4 Мониторинг (`health`)
- Проверки — отдельные функции: CPU, RAM, температура, напряжение, свободное место, аптайм/внезапные
  перезагрузки, состояние WAN и LTE (уровень сигнала), ping-цели, резолв DNS, наличие обновлений RouterOS,
  срок действия сертификатов.
- У каждой проверки пороги `warn`/`crit` и гистерезис (N подряд для смены состояния).
- События только при смене состояния (ok → warn → crit → ok), плюс сводка по запросу и раз в сутки.

### 3.5 WireGuard и трафик (`wg`, `traffic`)
- Профиль туннеля: интерфейс, проверочные адреса, маршруты для переключения (по комментарию), пороги.
  Обобщает текущую ручную схему `wg-health` / `wg-routes-on/off` / `wg-flush-web`.
- Состояния `up` / `degraded` / `down`; быстрое отключение, возврат после N успешных проверок; сброс
  веб-соединений при переключении.
- История падений: начало, конец, длительность, причина — в файл; статистика за сутки/неделю.
- Учёт трафика по интерфейсам: сутки и месяц, корректная обработка сброса счётчиков при перезагрузке,
  пороги по объёму (например, для LTE) с уведомлением.

## 4. Этапы

| Этап | Что | Результат |
|---|---|---|
| **0. Инфраструктура** | Репо, соглашения, тестовый **CHR** в Hyper-V на `hvhost`, `tools/` для выкладки на CHR по SSH и проверки синтаксиса. Проверка допущений из раздела 1. | Всё разрабатывается и тестируется на CHR, боевой роутер не трогаем. |
| **1. Ядро** | Загрузчик, `rhLog`, `rhConfig`, `rhState`, `rhEvent`, `rhPkg` (install/remove/list), `bootstrap.rsc`, `manifest.json`. | Модуль-пример ставится и удаляется с GitHub. |
| **2. Уведомления** | Шина + Telegram + e-mail. | События ядра приходят в Telegram. |
| **3. WireGuard** | Модуль `wg`, перенос текущей схемы переключения на боевом роутере, история падений. | Ручные скрипты `wg-*` заменены модулем. |
| **4. Health** | Базовые проверки и пороги. | Сводка и предупреждения в Telegram. |
| **5. Трафик** | Учёт по интерфейсам, суточные/месячные итоги. | Отчёт по запросу и по расписанию. |
| **6. Telegram-управление** | Polling, белый список, реестр команд, подтверждения. | Управление модулями из чата. |
| **7. Обновления** | `rhPkg check/update/rollback`, каналы по тегам. | Уведомление о новых версиях, обновление в одну команду. |
| **8. Каналы** | ntfy, webhook, WhatsApp, Viber. | По необходимости. |

Перенос на боевой роутер — только после проверки на CHR и с бэкапом (как `mikrotik-backup/` для текущей схемы).

## 5. Открытые вопросы
- Лицензия для публичного репозитория (MIT / Apache-2.0 / без лицензии).
- Где хранить состояние: flash или `/usb1` (на текущем роутере USB есть).
- Один бот на уведомления и управление или два отдельных.
- Шлюз для WhatsApp и условия Viber.
- Нужна ли поддержка нескольких роутеров (общий бот, имя роутера в сообщениях) — влияет на формат событий.
